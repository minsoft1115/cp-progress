# Capture & Verbose (`-v` 주입·캡처·중계)

Managed 모드에서 `cprog`가 `cp`의 출력을 어떻게 다루는지, 그리고 `-v`를 왜 "파싱"이 아니라
"타이밍 + 활동표시"로만 쓰는지 정의한다.

## 왜 캡처가 필요한가 (그리고 왜 byte-identical이 깨지는가)

- footer 아래에 바를 고정하고 로그를 위에서 스크롤시키려면, `cprog`가 **터미널의 유일한
  기록자(sole writer)** 여야 한다. 그래야 "footer 지우기 → cp 바이트 쓰기 → footer 다시
  그리기"를 깨짐 없이 할 수 있다.
- 그래서 managed 모드에서는 `cp`의 stdout/stderr를 **inherit이 아니라 capture(pipe)** 해서,
  `cprog`가 받아 다시 써준다(relay).
- 이 때문에 **managed 모드 출력은 순정 `cp`와 바이트 동일이 아니다**: `-v`가 주입되고,
  bytes가 inherit이 아니라 중계된다(순서·버퍼링이 미세하게 다를 수 있음).
- 단 **passthrough 모드는 캡처하지 않으므로 바이트 동일**을 유지한다. (대화형 managed
  모드는 사람이 보는 화면이라 byte-identical이 중요하지 않다.)

## ⚠️ 출력 버퍼링 — `-v`를 실시간으로 받으려면 라인버퍼 강제 필수

**이 설계에서 가장 중요한 제약이다.**

`cp`는 stdout이 **파이프(= 캡처하는 경우)이면 block-buffering** 한다. `-v` 줄이 복사 중에는
안 나오다가 **끝에 한꺼번에** 몰려 나온다. 그대로 두면:
- 스크롤 활동표시 = 복사 내내 빈 화면 → **"살아있음" 신호 실패**
- 줄경계 타이밍 = 복사 중 펄스 없음 → **느린 파일 감지 불가**

즉 캡처하는 순간 `-v`의 실시간성이 죽는다.

**해결: `cp`를 `stdbuf -oL`로 감싸 라인버퍼를 강제한다.**

```
stdbuf -oL cp -v <args...>
```

`stdbuf -oL`은 `cp`의 stdio stdout을 line-buffered로 바꿔 매 `\n`마다 flush시키므로, `-v`
줄이 파일마다 실시간으로 도착한다.

### 왜 `stdbuf`인가 (대안 비교)
`cp`가 라인버퍼하게 만드는 길은 둘이다:
- **`cp` stdout에 PTY를 물리기** — tty는 line-buffered라 자연히 실시간이 된다. 하지만 PTY
  master/slave·raw 모드·`\r\n` 쿠킹 등 복잡도를 도입한다(‑ `cprog`가 두지 않는 계층).
- **`stdbuf -oL`로 감싸기** — 명령 접두어 하나. 훨씬 단순하다. `cprog`는 이걸 쓴다.

### 버전 바닥과 feature-detect
managed 모드의 실질 버전 바닥은 `cp`가 아니라 **`stdbuf`(coreutils 7.5, 2009 도입)** 이다.
`cp -v`의 파일별 출력 자체는 버전 제한이 없고, 진행 계산은 `st_size` 기반이라 모든 버전에서
동작한다(‑ `copy_file_range`로 `pos`가 죽는 9.0+에서도). 따라서:
- **버전 번호를 파싱하지 않는다**(‑ 취약). `stdbuf`가 실행 가능한지 **feature-detect**만 한다.
- `stdbuf`가 없거나 동작 안 하면 → **passthrough**.

### stdbuf 사용 시 주의점
- **`stdbuf` 가용성:** coreutils라 `cp`가 있으면 거의 항상 있음. 없으면 → managed 조건 실패로
  **passthrough**로 폴백(라이브 UI를 약속만 하고 못 지키는 것보다 깔끔). runtime-model 참조.
- **PID 안정성 OK:** `stdbuf`가 `cp`를 `exec`하므로 **PID가 그대로 `cp`가 된다**(exec는 PID
  유지). `/proc/<pid>/fd`는 그대로 `cp`의 fd를 읽는다.
- **stderr는 이미 unbuffered:** glibc가 stderr를 버퍼 안 하므로 `cp` 에러는 `-oL` 없이도
  즉시 온다. stdout만 `-oL`이면 충분.
- **setuid 주의:** `stdbuf`는 `LD_PRELOAD`로 동작하는데 setuid 바이너리는 `LD_PRELOAD`를
  무시한다. `cp`는 보통 setuid가 아니라 무방(‑ 극히 드문 환경만 degrade).
- **relay는 즉시:** 라인버퍼로 온 바이트를 `cprog`가 **또 버퍼하면 안 된다** — 받는 즉시
  터미널로 흘려야 실시간이 유지된다(개행 대기 금지).

## `-v` 주입

- managed 모드에서 `cp` 인자에 `-v`가 없으면 주입한다. (그리고 위 `stdbuf -oL`로 감싼다.)
- **`QUOTING_STYLE=shell-escape`만 환경으로 고정**한다 — 파일명에 개행이 들어가도 한 줄로
  escape되게 해 버전 무관하게 안전하게 한다.
  - ⚠️ **`LC_ALL=C`는 걸지 않는다.** cprog는 `-v` 내용을 파싱하지 않으므로 로케일 안정화가
    이득이 없고, 오히려 C 로케일에선 비-ASCII 파일명(예: 한글)과 `cp`의 메시지가 옥타
    이스케이프(`$'\352\260\234...'`)로 깨져 사용자 화면만 망가진다. 사용자 로케일 그대로
    두어 `-v` 출력이 읽히게 한다.
  - ⚠️ **이 env 고정은 managed 모드에서만.** passthrough는 env를 절대 안 건드린다(바이트 동일).
- 사용자가 이미 `-v`를 줬는지 추적한다 — 오직 **이중 주입 방지**용. 표시 여부는 구분하지
  않는다(아래).

## `-v`를 "파싱하지 않는다"

`cprog`는 파일 개수를 세지 않는다. 따라서 `'src' -> 'dst'`의 **내용을 파싱하지 않는다.**
캡처 스트림에서 두 가지만 본다:

1. **바이트 그대로 로그 영역에 중계** — 화면에 그대로 보여줌(활동 표시).
2. **줄 경계(newline)만 감지** — 새 줄 하나 = "새 항목 시작" 펄스. 이걸로 느린 파일을 판정한다
   (아래 타이밍).

즉 `-v`의 `src`/`dst` 텍스트를 추출하지 않는다. 그래서:
- quote 처리, ` -> ` 분리, unquote 같은 파싱 파편성이 **전혀 없다.**
- 파일명에 개행(`\n`)이 있어도(리눅스에서 합법) `cprog` 로직엔 무의미하다. (참고: 현대 coreutils는
  `-v`에서 `\n`을 `$'\n'`으로 escape하므로 실제로는 한 줄로 온다. 설령 raw로 오더라도
  "펄스가 하나 더" 생기는 정도라 무해하다.)

## 느린 파일 타이밍

```
새 -v 줄 도착        → "현재 항목 시작" 시각 기록
다음 -v 줄 / cp 종료 → 이전 항목 끝
경과 > SLOW_THRESHOLD(기본 100ms)  → 현재 항목이 "느린 파일" → footer 바 켬
경과 < 임계 (다음 줄이 곧 옴)       → 빠른 파일/디렉터리 → 바 안 켬
```

바를 켤 때 실제 파일 경로·크기는 `-v`가 아니라
[`progress-model.md`](./progress-model.md)의 `/proc`+`stat`에서 얻는다.

### 핵심 가정: `cp`는 한 번에 한 파일
`-v` 펄스로 "느림"을 판정한 뒤 `/proc`에서 현재 파일을 찾는데, 이 둘이 **같은 파일**이라는
보장은 **`cp`가 파일을 순차적으로 복사**한다는 사실에 의존한다(‑ `cp`는 여러 파일을 동시
복사하지 않는다). 이 가정이 깨지는 도구를 감싸면 바가 엉뚱한 파일을 가리킬 수 있다 —
`cprog`는 `cp` 전용이므로 안전하다.

## 중계는 best-effort (cp exit code 절대 안 덮음)

`cp`가 성공(exit 0)했는데 relay/footer 쓰기가 실패(예: EPIPE)해도, 그 실패가 **`cp`의
결과를 바꾸면 안 된다.** 모든 중계·렌더는 무음 best-effort로(‑ `let _ = ...`, 별도 경고 타입
없음), exit code는 언제나 `cp`에서 나온다.

## stderr

- `cp`의 stderr(에러)도 캡처해 로그 영역에 중계한다(sole-writer라 하나의 기록자 유지).
- stdout(‑v)과 stderr(에러)의 상대 출력 순서는 두 파이프 중계라 순정과 미세하게 다를 수
  있다 — "알려진 한계"로 둔다.

## 요약: `-v`가 하는 일 / 안 하는 일

| 한다 | 안 한다 |
|---|---|
| 스크롤 활동 표시(그대로 중계) | 개수 세기 |
| 줄 경계 = 느린 파일 타이밍 | `src`/`dst` 경로 파싱 |
| — | quote/unquote/`->` 분리 |
