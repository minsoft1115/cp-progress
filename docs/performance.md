# Performance (성능 기준선)

cprog가 `cp`에 얹는 **오버헤드의 실측 기록**이다. 회귀가 생겼을 때 비교할 기준선이고, 동시에
"부하가 적다"는 주장이 어디까지 참인지 정직하게 적어두는 곳이다.

> 이 수치들은 **환경에 종속적인 관찰**이지 불변식이 아니다. 그래서 CI 게이트로 걸지 않고
> 문서에 기록한다 — 자동화할 수 있는 것은 [`testing.md`](./testing.md)의 결정론적 테스트다.
> 재현 스크립트는 [`scripts/bench.py`](../scripts/bench.py).

## 왜 이렇게 재나

**오버헤드는 바이트 수가 아니라 파일 개수에 비례한다.** 복사 자체는 `cp`가 하고 cprog는 데이터
경로를 건드리지 않는다. cprog가 파일마다 하는 일은 `-v` 줄 하나를 읽고(타이밍), 요청받았으면
중계하는 것뿐이다. 그래서:

| | 재는 방법 | 이유 |
|---|---|---|
| **저장장치** | **tmpfs**(`/dev/shm`) | 디스크 변동성과 페이지 캐시를 방정식에서 뺀다. 남는 차이는 전부 cprog 것 |
| **지표** | 벽시계 + **프로세스 트리 CPU**(`wait4`의 rusage) | 벽시계는 I/O 대기가 지배해 둔감하다. CPU는 추가된 작업량을 직접 보여준다 |
| **시나리오** | 소파일 대량 / 대용량 단일 | 전자가 최악, 후자가 진행바가 실제로 쓰이는 경우 |
| **분해** | `cp` → `stdbuf -oL cp -v` → `cprog` | `-v` 비용은 **`cp`가 내는 것**이다. 빼고 봐야 cprog 고유 비용이 나온다 |
| **순서** | 변형을 **교대**로 반복, 중앙값 | 한 방향으로 몰아 돌리면 시스템 상태 변화가 결과에 섞인다 |

교대 측정이 특히 중요하다. 초기 측정에서 "벽시계 42% → 19% 개선"으로 보였던 것이 같은 실행 안에
두 바이너리를 교대로 넣자 **차이 없음(노이즈)** 으로 드러난 적이 있다.

## 2026-07-31 기준선 (v0.6.0)

측정 환경: tmpfs, 7회 교대 반복, 중앙값. `cprog 고유 CPU`는 `stdbuf -oL cp -v` 대비 증가분.
**버전을 라벨에 박는다** — "현재"로 적으면 다음 릴리스에서 어느 코드의 수치인지 알 수 없다.

### 파일 20,000개 × 4 KiB (오버헤드가 드러나는 경우)

| | 벽시계 | CPU 합 | cprog 고유 CPU |
|---|---|---|---|
| `cp` | 0.337s | 0.337s | — |
| `stdbuf -oL cp -v` | 0.383s | 0.389s | — |
| cprog **v0.3.0** | 0.404s | 0.711s | **+0.329s** |
| cprog **v0.6.0, `-v` 없이** | **0.370s** | **0.452s** | **+0.069s** |
| cprog **v0.6.0, `-v` 있음** | 0.377s | 0.675s | +0.289s |

- 기본 사용(`-v` 없이) 고유 CPU가 **+0.329s → +0.069s, 79% 감소**했다. 이 비교는 두 버전을
  **같은 실행 안에서 교대로** 재서 얻은 것이다.
- `-v`를 준 경우는 +0.289s로 거의 그대로다. **당연하다** — 중계를 요청한 사용자가 그 비용을
  내는 것이고, 예전에는 아무것도 요청하지 않은 사용자가 최대 비용을 냈다. 이 설계 변경(#20)의
  핵심은 총량을 줄인 게 아니라 **비용을 요청과 정렬**한 것이다.
- 남은 +0.069s는 파이프 `read` 1회와 타이밍용 `Instant::now()` 1회다. 진행바를 그리려면
  원리상 필요하다.

### 파일 1개 × 4 GiB (진행바가 실제로 쓰이는 경우)

| | 벽시계 | CPU 합 | cprog 고유 CPU |
|---|---|---|---|
| `cp` | 1.783s | 1.782s | — |
| `stdbuf -oL cp -v` | 1.783s | 1.782s | — |
| cprog **v0.3.0** | 1.807s | 1.792s | +0.010s |
| cprog **v0.6.0, `-v` 없이** | 1.788s | 1.791s | +0.009s |
| cprog **v0.6.0, `-v` 있음** | 1.787s | 1.790s | +0.008s |

고유 CPU가 세 버전 모두 `cp` 자신의 실행별 변동폭 수준이다 — 파일당 비용이 곱해지지 않기
때문이며 설계 의도대로다.

### 종료 지연: 벽시계가 샘플 주기 격자에 붙던 문제 (v0.6.0에서 제거)

**v0.5.0까지 cprog의 벽시계는 `sample_interval`(기본 100 ms)의 배수로 올림됐다.** 샘플러 루프가
`stop`을 위에서 읽고 아래에서 그냥 잤기 때문에, teardown이 플래그를 세워도
`sampler_thread.join()`이 진행 중인 sleep을 기다렸다 — **모든 managed 복사가 `cp`보다 최대 한
샘플 주기를 더 살았다.** 작은 복사에서는 이것이 벽시계 오버헤드의 지배 항이었다.

원인 규명은 knob을 흔들어서 했다(20,000개 × 4 KiB, `-rv`, 12회 전수):

| knob | v0.5.0 | **v0.6.0** |
|---|---|---|
| 기본 `sample=100`, `tick=125` | 0.40 ×1, 0.50 ×10, 0.51 ×1 | 0.38 ×6, 0.39 ×4, 0.40 ×2 |
| `CPROG_SAMPLE_INTERVAL_MS=300` | **0.60 ×11**, 0.61 ×1 | 0.37 ×2, 0.38 ×3, 0.39 ×4, 0.40 ×3 |
| `CPROG_RENDER_TICK_MS=300` | 0.40 ×4, 0.50 ×8 (무관) | 0.37 ×1, 0.38 ×9, 0.39 ×2 (무관) |
| `CPROG_SAMPLE_INTERVAL_MS=25` | 0.38 ×1, 0.40 ×1, 0.43 ×9, 0.53 ×1 | 0.37 ×1, 0.38 ×6, 0.39 ×3, 0.40 ×2 |

v0.5.0에서는 `CPROG_SAMPLE_INTERVAL_MS`만이 격자를 옮겼고(`CPROG_RENDER_TICK_MS`는 무관),
v0.6.0에서는 **어느 knob도 벽시계를 움직이지 않는다** — 300 ms로 올려도 분포가 그대로다.
복사 시간을 바꿔가며 재면 계단이 사라진 것이 보인다(각 7회, `-r`):

| 파일 수 | `cp` | v0.5.0 | **v0.6.0** | 100 ms 격자 |
|---|---|---|---|---|
| 5,000 | 0.089s | 0.103s | **0.097s** | 0.100s |
| 10,000 | 0.170s | 0.204s | **0.190s** | 0.200s |
| 20,000 | 0.338s | 0.404s | **0.374s** | 0.400s |
| 30,000 | 0.508s | 0.604s | **0.558s** | 0.600s |
| 45,000 | 0.751s | 0.904s | **0.838s** | 0.900s |

v0.5.0 열은 격자에 정확히 앉아 있고, v0.6.0 열은 어느 칸에도 앉지 않는다 — `cp`의 시간에
실제 작업량만 더한 값이다.

**그래도 회귀 판정은 CPU로 한다.** 격자가 사라져 벽시계가 연속량이 됐지만, 벽시계는 여전히
I/O 대기가 지배해 둔감하다. 이 문서가 처음부터 CPU를 주 지표로 삼은 이유는 그대로다.

규칙 자체는 [`process-model.md`](./process-model.md#샘플링과-종료)에 있고,
`testing.md` D9 / `lib.rs::Stopper` 유닛 + `tests/managed.rs::teardown_does_not_wait_out_the_sampler_interval`이 고정한다.

## 측정 머신 특성: clocksource가 느리다

측정 머신의 clocksource가 `tsc`가 아니라 **`hpet`** 이다. vDSO 빠른 경로를 못 타서
`clock_gettime` 한 번이 **1,279 ns** 든다(TSC+vDSO 환경은 20~30 ns, 실측 확인).

`Instant::now()`가 그만큼 비싸므로 **위 수치는 일반적인 하드웨어에서의 상한**이다. 반대로
말하면 시계 호출을 줄이는 최적화의 효과가 이 머신에서 과대평가된다 — 다른 곳에서 재면 다르게
나온다는 뜻이니, 회귀 판정은 **같은 머신에서 교대 측정**한 값끼리만 비교해야 한다.

```
$ cat /sys/devices/system/clocksource/clocksource0/available_clocksource
hpet acpi_pm
```

## syscall 프로파일 (파일 2,000개, `strace -f -c`)

수치보다 **어디서 오는지**가 회귀 추적에 쓸모 있다.

| syscall | 파일당 | 출처 |
|---|---|---|
| `read` | 1.0 | 파이프에서 `-v` 줄 읽기 — 타이밍에 필요, 제거 불가 |
| `clock_gettime` | 상황에 따라 | 메인 스레드가 빈 큐에서 대기 + 펄스 기록 |
| `write`·`futex`·할당 | `-v` 있을 때만 | 중계 경로 |

`ioctl`은 파일당 1회쯤 보이는데 **`cp` 자신의 reflink 시도**(`BTRFS_IOC_CLONE`)이고 cprog와
무관하다 — 프로파일을 볼 때 헷갈리기 쉬워 적어둔다.

## 재현

비교 대상은 **worktree로** 빌드한다 — 작업 트리에서 `git checkout`으로 왔다 갔다 하면 빌드
산출물과 lockfile이 섞이고, 중간에 중단되면 트리가 다른 커밋에 남는다.

```bash
cargo build --release && cp target/release/cprog /tmp/cprog-new
git worktree add --detach /tmp/wt-old v0.3.0
(cd /tmp/wt-old && cargo build --release --offline && cp target/release/cprog /tmp/cprog-old)
CPROG_OLD=/tmp/cprog-old CPROG_NEW=/tmp/cprog-new python3 scripts/bench.py
git worktree remove /tmp/wt-old
```

`CPROG_OLD` / `CPROG_NEW`로 비교 대상을 바꾼다. tmpfs에 최대 8 GiB 정도를 쓰므로 여유를 확인하고
돌린다. **다른 부하와 겹치면 안 된다** — CPU 시간을 재는 측정이라 동시에 돌린 빌드나 테스트가
그대로 수치에 들어간다.
