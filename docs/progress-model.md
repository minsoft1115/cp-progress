# Progress Model (진행 계산)

느린 파일의 per-file 바를 어떻게 계산하는지 정의한다. 외부 도구 없이, `cp`의 협조 없이,
커널의 `/proc`와 `stat`만 쓴다.

> **근거.** GNU coreutils 9.x의 `cp`는 `copy_file_range`를 쓰는데, 이 경로에서는 fd offset
> (`fdinfo: pos`)이 복사 내내 0으로 남고 `/proc/<pid>/io`의 `wchar`도 0이다. 복사를 따라
> 커지는 신호는 **대상 파일의 크기(`stat().st_size`)** 뿐이다. `cprog`는 이 위에 세운다.

## 핵심 신호: 대상 파일 크기

```
total   = stat(현재 원본).st_size     # 파일 시작 시 1회
done    = stat(현재 대상)             # cp가 그 파일을 쓰는 동안 폴링 (아래 "측정 기준" 참조)
percent = done / total
```

### 측정 기준(basis)은 파일마다 한 번만 정한다

`done`을 `st_size`로 재느냐 `st_blocks*512`로 재느냐는 **파일이 바뀔 때 한 번 정하고 그 파일 내내
고정**한다. 두 기준은 서로 반대 방향의 실패를 막기 때문에, 매 샘플 `min()`을 취하는 식으로는 둘 다
만족시킬 수 없다.

| 상황 | `st_size` | `st_blocks*512` | 옳은 기준 |
|---|---|---|---|
| 선할당(`fallocate`) 대상 | 시작부터 full | 실제 쓰기를 따라감 | **blocks** |
| sparse 대상(`cp --sparse=auto`) | 진짜 논리 길이 | 훨씬 작음(정상) | **size** |
| 압축 FS(btrfs `compress`) 대상 | 진짜 논리 길이 | 훨씬 작음(정상) | **size** |

판정 규칙(첫 샘플에서 1회):

```
원본이 sparse(src.blocks*512 < src.size)  → size 기준
  (대상이 sparse해지는 건 당연하므로 blocks로 재면 과소평가된다)
아니고, 첫 샘플에서 대상 size가 이미 total 이상인데 blocks가 total에 한참 못 미침
                                          → blocks 기준 (선할당으로 판정)
그 밖에 전부                               → size 기준 (기본값)
```

**기본값이 size인 이유:** blocks는 파일시스템 사정으로 실제 쓰기와 어긋나는 방향이 양쪽 모두다 —
압축·sparse에서는 작게, ext4의 speculative preallocation에서는 크게 나온다. size는 "논리적으로
어디까지 안착했나"를 곧이곧대로 말해주므로 기본으로 삼고, 선할당이 **적극적으로 확인될 때만**
blocks로 바꾼다.

`total`은 어느 기준에서도 원본의 `st_size`를 쓴다 — 사용자가 기대하는 "이 파일의 크기"가 그것이고,
비율의 분모가 흔들리지 않아야 하기 때문이다.

`st_size`는 inode의 파일 길이다. `cp`가 `write`/`copy_file_range`/`sendfile` 무엇으로
쓰든 대상이 커지면 증가하므로, **syscall 종류와 무관하게** 진행을 반영한다. 이게 `pos`와
io 카운터가 실패하는 곳에서도 되는 이유다.

원본이 아니라 **대상**을 재는 이유: 대상 크기는 "실제로 안착한 바이트"이고, 원본 read
위치는 read-ahead 캐시로 앞서갈 수 있다.

## 현재 파일을 찾는 법 (read-only 관찰)

바를 켤 시점(느린 파일 감지, [`capture-and-verbose.md`](./capture-and-verbose.md))에 `cp`의
열린 fd를 관찰한다. `cp`를 건드리지도, 막지도 않는다.

1. `/proc/<pid>/fd/`를 나열하고 각 항목을 `readlink`로 대상 경로로 푼다.
2. **정규 파일(regular file)** 만 남긴다(파이프·소켓·tty·디렉터리 제외). stdio(`fd ≤ 2`)도 뺀다.
3. **쓰기 모드 후보**를 모은다. 후보가 하나면 그게 대상이다.
4. 원본 쪽 fd → `stat` → `total`.

### 쓰기 후보가 둘 이상일 때 (상속된 fd 배제)

셸 리다이렉션이 만든 fd(`cprog a b 3>log`)는 close-on-exec이 아니라 **`cp`까지 상속된다.**
게다가 번호가 낮아 `cp`가 나중에 여는 진짜 대상보다 앞에 온다:

```
3 -> log       (쓰기)   ← 셸이 물려준 것
4 -> 원본      (읽기)
5 -> 진짜 대상 (쓰기)
```

그래서 "fd 순서상 첫 쓰기 fd"를 고르면 엉뚱한 파일을 가리킨다. 대신 **틱 사이에 크기가 자라는
fd**를 고른다 — 정의상 그게 지금 복사 중인 파일이다.

- 후보가 하나 → 그대로 사용(추가 `stat` 없음. 절대 다수가 이 경우다).
- 후보가 여럿 → 각 후보를 `stat`해 직전 틱과 비교하고, **가장 많이 자란 것**을 고른다.
- 아직 비교할 직전 값이 없거나 아무도 안 자랐으면 → 추측하지 않고 **직전에 고른 대상을 유지**하고,
  그것마저 없으면 이번 틱을 건너뛴다(`Skip`). 엉뚱한 파일의 진행을 보여주느니 잠깐 안 보이는 게 낫다.

### 원본은 fd 번호로 짝짓는다 (읽기 쪽 상속 fd 배제)

읽기 쪽에도 같은 문제가 있다. `cprog a b 3<other`처럼 셸이 물려준 **읽기** fd도 `cp`까지 상속되고,
번호가 낮아 진짜 원본보다 먼저 온다. 원본은 `total`의 출처라 잘못 고르면 비율 전체가 무의미해진다.

쓰기 쪽에서 쓴 "자라는 것" 규칙은 **여기 못 쓴다** — 원본은 읽기만 하므로 크기가 변하지 않는다.
대신 **fd 번호로 짝짓는다.** `cp`는 한 파일을 복사할 때 **원본을 열고 곧바로 대상을 열므로**,
지금 복사 중인 원본은 *고른 대상 fd보다 작은 읽기 fd 중 가장 큰 것* 이다.

```
3 -> other      (읽기)  ← 상속된 것. 대상에 더 가까운 읽기 fd가 있으므로 배제
4 -> 진짜 원본  (읽기)  ← 5보다 작은 읽기 fd 중 최대 → 선택
5 -> 진짜 대상  (쓰기)  ← 성장으로 고른 대상
```

대상보다 **위쪽** 번호의 읽기 fd(나중에 열린 무관한 파일)도 이 규칙으로 자연히 배제된다.
대상보다 작은 읽기 fd가 하나도 없으면 **추측하지 않고 원본 없음으로 둔다** — `total`이 미지가 되어
indeterminate 바로 그려질 뿐, 틀린 비율을 보여주지 않는다.

경로는 `readlink`가 준 **실제 경로**라 `-v` 텍스트를 unquote할 필요가 없다.

## rate / eta (현재 파일 기준)

`(시각, done)` 샘플을 짧은 rolling window에 담는다:

```
rate = (done_now − done_window_start) / (t_now − t_window_start)
eta  = (total − done) / rate       # rate 모르면 --:--
```

window(기본 ~1s)가 버스트 I/O를 평활화해 숫자가 튀지 않게 한다. **이 %/rate/eta는 현재
파일 하나에 대한 것**이다 — 전체 작업 값이 아니다.

## 샘플링 주기와 비용

- 대상 크기를 고정 주기(기본 100ms)로 `stat` 폴링한다. 렌더 tick과 독립.
- 각 샘플 = `readlink` 1회(현재 파일) + `stat` 1회 — hot inode 메타데이터 조회라 마이크로초.
  **파일 데이터는 안 읽으므로** 페이지 캐시 오염·cp 간섭 없음.
- **느린 파일에만** 이 폴링을 한다. 빠른 소파일은 바를 안 켜므로 stat도 안 한다 → 대량
  소파일에서 stat 폭발이 없다.

## 실패 처리

샘플러의 tick 결과는 **세 가지를 구분**한다. "못 읽었다"와 "잴 게 없다"는 화면에서 정반대를
뜻하기 때문이다:

| 결과 | 언제 | 화면 |
|---|---|---|
| `Sample` | 정상적으로 크기를 읽음 | 바 갱신 |
| `Skip` | 읽기가 **실패**(권한·일시적 오류) | **마지막 값 유지** — 깜빡이지 않게 |
| `Idle` | 잴 대상이 **없음**(파일 사이, 디렉터리 처리 중, 방금 끝나 fd가 닫힘) | **바를 내림** |

둘을 뭉뚱그려 "마지막 값 유지"로 처리하면, 느린 파일이 끝난 뒤에도 `-v` 펄스가 다음에 올 때까지
**정지된 바가 남는다**(`is_slow`는 다음 펄스에서야 풀리므로). 그래서 `Idle`은 값을 비운다.

- 실패한 샘플(`Skip`)은 건너뛰고 마지막 값 유지(권한·일시적 오류).
- 샘플링이 아예 안 되면 바만 안 보일 뿐 복사는 정상. `cp`가 언제나 authoritative.
- 자식의 `/proc`/`stat` 읽기는 같은 user일 때 정상(일반적). setuid/`sudo` cp면 못 읽어
  바가 안 뜰 뿐, 복사엔 영향 없음.

## 한계 (정직하게 명시)

- **preallocation**(`fallocate`): `cp`가 대상을 선할당하면 `st_size`가 한 번에 full로 튄다 →
  첫 샘플에서 이를 감지해 그 파일에 한해 **`st_blocks * 512`(실제 디스크 블록)** 기준으로 잰다.
- **reflink / copy-on-write**: 거의 즉시 완료 → 바가 100%로 점프(정확하지만 점진적이지 않음).
- **sparse 파일**: 원본에 hole이 있으면 `cp`는 기본값(`--sparse=auto`)으로 대상도 sparse하게
  만든다. 이때 대상의 `st_blocks*512`는 논리 길이보다 훨씬 작은 게 **정상**이므로 size 기준으로
  잰다. 실제로 쓰인 바이트가 아니라 논리적 진행을 세는 것이라, hole을 건너뛰는 구간에서는
  rate가 실제 디스크 처리량보다 높게 보일 수 있다.
- **압축 파일시스템**(btrfs `compress`, ZFS) 및 `st_blocks`를 0으로 보고하는 파일시스템:
  같은 이유로 size 기준이라 영향받지 않는다.
- **아주 빠른 파일**: 첫 샘플 전에 끝남 → 바 없이 지나감(의도된 동작).
- **비-리눅스**: `/proc` 없음 → managed 불가, passthrough로.

## 왜 `pos`가 아니라 `st_size`인가 (참고)

커널 `fdinfo`의 `pos`를 읽는 방식(일부 외부 진행률 도구가 쓰는)은 `copy_file_range` 때문에
**coreutils 9.x에서 진행을 못 잡는다**(위 근거). `cprog`는 대상 `st_size`를 직접 읽으므로
외부 프로세스·PTY 없이 단순하면서도 현대 `cp`에서 정확하다.
